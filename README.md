# AIRailway — аналитика пассажиропотока вокзала в Telegram

Telegram-бот для управляющего крупным московским вокзалом: загружает суточные выгрузки по пассажиропотоку в PostgreSQL, считает почасовые зоны нагрузки (зелёная / жёлтая / красная) для двух потоков — прибытия и отправления, — моделирует пропускную способность при неполном оборудовании и раз в сутки присылает дайджест-прогноз на неделю вперёд. Ответы оформляются естественным языком через DeepSeek API, опираясь только на посчитанные числа.

---

## Задача

Вокзал — это два встречных людских потока в одних и тех же коридорах: прибывшие пассажиры идут через турникеты на выход, отправляющиеся — через рамки на вход. Управляющему нужно заранее понимать, в какие часы и на каком оборудовании образуется «пробка»:

- сколько минут займёт проход потока в конкретный час при текущем числе работающих турникетов и рамок;
- какие часы на неделе будут зелёными, жёлтыми и красными;
- что будет, если часть оборудования выйдет из строя.

Исходные данные — суточные выгрузки (почасовые пассажиропотоки, число поездов и работающего оборудования) и суточная статистика транспортного узла. Нужен был инструмент, который превращает эти выгрузки в понятный ответ на вопрос «что будет завтра и что делать с оборудованием», без ручных пересчётов в Excel.

## Как это работает

```
Исходные выгрузки (Excel/CSV, локально, вне репозитория)
      │
      ▼
scripts/load_excel.py  ── авто-определение формата (плоская таблица / ПТВ) → UPSERT в PostgreSQL
      │                     hourly_data  · ptv_data  · ptv_hourly_data
      ▼
src/analytics/calculator.py ── математика зон по часам, два независимых потока
      │        пасс/поезд × сек_прохода / работающее_оборудование / 60 = минуты → зона
      │        + calculate_min_equipment: минимум оборудования для зелёной зоны
      ▼
src/llm/deepseek.py ── строгий промпт → готовый HTML для Telegram
      │                 (при недоступности API — собственный fallback-форматтер)
      ▼
src/bot/handlers.py ── 4 кнопки: статус · сегодня · неделя · моделирование
      ▲
      │
src/bot/scheduler.py ── APScheduler: ежедневный дайджест на 6 дней вперёд (нормативное оборудование 17/17)

Обогащение прогноза «на сегодня»:
  src/parsers/weather.py (wttr.in)  +  src/parsers/events.py (Kudago)  +  баллы пробок по дням недели

Слой регламентов (RAG, часть архитектуры v1):
  src/loaders/doc_loader.py → PDF/DOCX → чанки → sentence-transformers → pgvector
  src/analytics/rag.py → семантический поиск фрагментов регламентов
```

## Что показывает проект с инженерной стороны

- **Разделение потоков.** Прибытие и отправление считаются независимо (турникеты vs рамки и разные времена прохода), зона часа — худшая из двух. Это ближе к реальности, чем единый «пассажиропоток»: узкие места у двух потоков разные.
- **Математика отделена от языка.** DeepSeek не считает — он только оформляет уже посчитанные числа по строгому шаблону. Все зоны, минуты и рекомендации по оборудованию получены кодом; LLM подставляет их в текст.
- **Деградация без потери функции.** Если DeepSeek недоступен, каждый сценарий имеет собственный fallback-форматтер (`_build_*_fallback`) — бот отдаёт тот же результат в HTML, собранный локально.
- **Моделирование как стресс-тест.** Кнопка «Моделирование» пересчитывает день с произвольным числом работающих рамок и турникетов — можно посмотреть, при каком парке оборудования час уходит в красную зону.
- **Нормативный сценарий для прогноза.** Недельный дайджест считает будущие дни с полным парком оборудования (17/17), а данные берёт по тому же дню недели из истории — то есть отвечает на вопрос «что будет, если работать на всех».
- **Устойчивость к сети.** Отдельный watchdog-поток каждые 30 секунд проверяет DNS `api.telegram.org` и после трёх отказов жёстко завершает процесс; `run_bot.bat` поднимает бота заново. Длинные сообщения режутся по 4000 символов — лимит Telegram.
- **Контроль доступа и аудит.** Вход по паролю (`BOT_PASSWORD`) с персистентной авторизацией в БД, логирование активности пользователей и всех обращений к LLM (`forecast_log`).
- **Безопасность.** Все секреты и параметры — только через переменные окружения; реальных данных, выгрузок и логов в репозитории нет.

## Запуск

```bash
python -m venv .venv
.venv\Scripts\activate           # Windows
pip install -r requirements.txt

copy .env.example .env           # заполнить доступы и параметры

# PostgreSQL: создать базу и включить расширение для векторного поиска
psql -c "CREATE DATABASE airailway;"
psql -d airailway -c "CREATE EXTENSION IF NOT EXISTS vector;"

# Положить исходные выгрузки в data/ (в репозитории их нет) и загрузить
python -m scripts.load_excel
# или конкретный файл:
python -m scripts.load_excel "data/выгрузка.xlsx"

# Запуск бота
python -m src.bot.main
```

На Windows можно использовать `setup.bat` (создаёт venv и ставит зависимости) и `run_bot.bat` (автоперезапуск бота).

## Переменные окружения

Полный список с комментариями — в `.env.example`. Основные:

- **Доступы:** `TELEGRAM_TOKEN`, `TELEGRAM_CHAT_ID`, `DATABASE_URL`, `DEEPSEEK_API_KEY`, `BOT_PASSWORD`.
- **LLM:** `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`.
- **Математика зон:** `TURNSTILE_PASS_SECONDS`, `FRAME_PASS_SECONDS`, `FRAMES_TOTAL`, `TURNSTILES_TOTAL`, `ZONE_GREEN_MAX`, `ZONE_YELLOW_MAX`, `PASSENGERS_PER_TRAIN_THRESHOLD`.
- **Расписание:** `DAILY_DIGEST_HOUR`, `DAILY_DIGEST_MINUTE` (МСК).
- **Вокзал и погода:** `STATION_NAME`, `STATION_LAT`, `STATION_LON`, `WEATHER_CITY`.
- **Данные:** `DATA_DIR`.

## Ограничения и что дальше

- Прогноз строится не на ML-модели, а на подстановке исторических данных того же дня недели; сезонность и аномалии не учитываются.
- Погода, мероприятия и баллы пробок влияют только на текст ответа «на сегодня», но не на математику зон.
- Слой регламентов (RAG: `aggregator.py`, `rag.py`, `doc_loader.py`, `csv_loader.py`) — часть архитектуры v1; в текущем четырёхкнопочном сценарии бота он не задействован и требует доработки моделей БД (`PassengerFlow`, `RegulationChunk`).
- Расчёты выполнялись на тестовых данных; промышленная валидация на длинной истории не проводилась.
